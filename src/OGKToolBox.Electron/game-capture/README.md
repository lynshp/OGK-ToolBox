# Local player capture and queued edits

Module 1.0.14 decodes task/configuration DTOs with a bounded managed parser instead of Unity native `FromJson`. It rejects duplicate keys, wrong types and missing edited values before claim. The login-entry tests now cover JSON decoding, identity selection, task claim, medal/shizuku application, repeated hooks and interrupted receipts. `edits-diagnostics.json` records only a fixed execution stage, exception type and time, including failures before a task is identified. The 1.0.13 live failure had only `needs-review` with the task still pending; its exact native exception was not recorded, so actual Unity login remains a required validation.

The Mod publishes the current capture session alongside its heartbeat. Electron reports **已采集 · 持续同步** after that session's six required read types and observed pagination chains are complete, while continuing to ingest later reads and settlements. Older completed sessions cannot complete a new login's status; an expired heartbeat still means the game is offline.

Module 1.0.13 adds `PlayerEdits.cs`: explicit user commands under `player-data/edits` are bound to configured server authority, access code and native short keychip ID. A postfix on `UserManager.initializeOnLogin` runs on the game's login thread after all data loading and initialization. Only accepted, non-guest logins apply commands. Resources use native add/subtract methods; score edits (MuNET only) use native setters, current analysis maxima and native rating/BP recalculation. Field masks preserve unedited live score values. No archive, cabinet count or native backup is directly rewritten.

Electron publishes an immutable `.pending.json` command. The Mod validates it, atomically claims `.active.json`, checks the claimed bytes and then mutates memory once. Confirmed native saves remove only included resource/chart keys from the pending set. All accepted batches produce `.complete.json`; gameplay earnings/spending are never reset to the original target on save. Already satisfied loaded values need no upload. A process interruption or application failure leaves the active receipt for review, never automatic replay. Cancel is available before claim; clearing an active receipt requires the game to be stopped and does not undo changes already applied. Commands/receipts contain local card and machine identity; do not distribute them. Live Unity/Harmony and real-server acceptance still need private game testing.

Module 1.0.12 attaches the originating capture session ID to accepted Upsert observations. Electron now materializes a separate post-save archive from the complete login snapshot and successful keyed deltas, preserving untouched scores/inventory and advancing the existing automatic selection revision. Failed or foreign observations and incomplete login pagination do not advance it; repeated scans and deletion remain idempotent. Legacy 1.0.11 samples require a unique latest preceding login with matching identity and endpoint.

The backup observer can read a completed backup while amdaemon retains a writable handle. It requires matching consecutive hashes, stable file metadata, and rechecks the original successful native request, non-busy state, non-dirty SettingExt and actual counter after hashing. This does not generate or increment native counters.

`PlayerCapture.cs` is a BepInEx 5 / Harmony 2 plugin for the Unity Mono game. It observes six core read responses (`GetUserData/Music/Card/Character/Item/Option`) and optional `GetUserActivity`, `GetUserRecentRating` and `GetUserRatinglog` responses and writes local records under `Tools/OGKToolBox/player-data/captures`. Module 1.0.13 retains the game's successful `GameLogin` observation to identify the card actually read and the independent optional machine-information observer. The module never sends its own requests, changes network responses or disables encryption. Explicitly queued edits change native user objects after login; the game uploads them through its normal save path. The Electron page installs or updates it only while the game is stopped. Previously enabled installations show an **更新模块** action when their DLL differs from the bundled module. Stopping capture removes the enable marker; existing archives remain.

Module 1.0.6 adds optional Preview diagnostics under the separate `Tools/OGKToolBox/player-data/preview-observations` directory. Only an already parsed `GetUserPreview` response with matching positive numeric request/response user IDs, boolean login/warning states and integer ban state can be recorded. Parsed login or ban state is evidence, not confirmation that GameLogin succeeded. The record preserves the game's original request JSON and response JSON, the connection and startup machine snapshot. A separate optional postfix observes the game's send-path `getUserAgent` result for the exact already mapped Preview query; it does not call that function itself or replace its return value. This observes the send-path calculation, not a raw HTTP packet capture, and does not establish that an external upload is indistinguishable from the game.

Preview diagnostics use random GUID filenames, at most 128 records per game run, a 1 MiB UTF-8 request limit and an 8 MiB UTF-8 response limit. They stay local and contain sensitive player/connection information: never log, bundle, publish or return their raw contents to the renderer. Existing records remain when capture stops; the per-run cap is not a global retention limit. Missing or failed Preview hooks leave the six ordinary capture APIs, session, ownership, status and machine observer unchanged, with only a separate anonymous `preview-capture-status.txt`. Preview diagnostics do not create player profiles, identity sidecars, ordinary capture sessions or save archives, and are not replayed by ordinary capture refresh. Recording a Preview does not resolve an HTTP 401 or prove live Harmony compatibility; compare only records whose current player, server and machine scope have been independently verified.

The independent optional native-save observer writes under `Tools/OGKToolBox/player-data/upsert-observations`. Module 1.0.9 binds the original `NetHttpClient.Create` return value to the exact game-created query. A prefix on the larger `request(byte[],string,bool)` observes the actual UTF-8 JSON bytes and User-Agent supplied by the game before native compression/encryption. A postfix on the larger `onCompleted()` observes only the original decoded response fields when `state_ == 3`, `errorCode_ == 0` and HTTP status is 2xx. It copies exactly `responseLength_` bytes, never unused buffer capacity. These four private status/length fields are Int32 and `response_` is Byte[] in the statically checked game. It never calls native factories, sends, getters, parsers, serializers or completion routines. It does not rely on the small `getResponse` getter being patched. This is a passive observation of actual transport inputs and decoded outputs, not final compressed/encrypted HTTP bytes or evidence that another upload is indistinguishable from the game.

The previous optional `getRequest`, `getUserAgent` and parsed `setResponse` observers remain as a separate fallback on the same query lifetime. Actual transport bytes and agent arguments become authoritative once observed; later small-method observations cannot replace them. Query and transport paths consume the same lifetime once, preventing duplicate records. The client is held only by a weak reference. A replacement client is allowed only inside the exact query's original `Packet.reset()` context, retains the first generation/time, and clears the previous request evidence. Old clients, value-equal foreign clients and a collected former client outside reset cannot borrow the new request. Diagnostic reset context is restored on both normal and exceptional exits without changing the core packet context or the game's original exception.

Module 1.0.10 fixes a diagnostic gap: a rejected legacy serialized request or agent, or a later failed ownership/lifetime check, previously could retire the exact query silently and leave `transport-client-observed` as the last stage. Rejections now retain a fixed anonymous reason before releasing the pending request. The same owner, native struct, source, generation, TTL, size and shared memory guards remain enforced. This repair diagnoses an observation gap; it does not identify the real cause of an earlier server HTTP 500, relax validation, create a native sample, or change the upload writer.

## Explicit best-score synchronization

The separate `player-best-upload.ts` adapter is used only by the player's explicit best-score synchronization action, while the existing read adapter remains read-only. It resolves the current configured server and selected known card through ALL.Net/AimeDB again, validates the local archive's server/card scope, reads and saves a separate target backup, then sends only improved `UserMusicDetail` rows in `UpsertUserAllApi`. The packet includes `isNewMusicDetailList` with the game's per-row new/existing markers. It omits all other `UserAll` lists and `userData`: no inventory, currency, progress, logs, rating bases, or options are transferred. Higher target best scores and flags remain; target play counts and other music metadata remain, while newly transferred charts start with zero play count. Empty charts are skipped. No login or logout is sent.

Explicit synchronization uses the installed game's API User-Agent for all pre-upload reads, writes and verification reads, including every page and optional activity read. Local game 1.50 `NetPacketUtil.getUserAgent` formats the uppercase PBKDF2-HMAC-SHA1 digest of the API name (first eight digest-salt bytes, 64 iterations, 16 output bytes), followed by `#` and the freshly resolved target player ID. `player-game-protocol.ts` statically reads the game's `System.loadResources` and fixed-key initializer with the application's already-shipped Mono.Cecil parser, then resolves the exact Unity ResourceManager/TextAsset reference with its already-shipped AssetsTools.NET parser. The keyed 32-byte BLAKE2b digest supplies the salt. The game assembly is never loaded or executed. The hidden Windows PowerShell child and main-process memory retain these inputs only during derivation; no commercial key, salt, resource contents or actual player identity is bundled, written to disk, logged, or sent to the renderer. Unknown loader/algorithm shapes and missing parser or game resources fail before network discovery, preserving the local merge.

During synchronization, ALL.Net PowerOn omits the User-Agent header; its original native AMDaemon User-Agent has not been established and no replacement constant is invented. No synchronization request uses the ordinary adapter's `OGKToolBox/1.0` identifier. Independent standalone save fetching keeps its existing compatible read adapter and identifier. Game API transport remains the existing compatible plaintext JSON/deflate path: adopting the game's User-Agent does not implement encrypted game requests or a complete game session. The music-only payload, absent login/logout and logs, and zero-play imported charts can still distinguish this operation from ordinary game saving. There is no claim that the server cannot recognize external synchronization.

This music-only delta shape was checked against local game 1.50 `UpsertUserAllRequest`, `UserAll`, `UserMusicDetail`, and `PacketUpsertUserAll` metadata, without executing the game. The primary [AquaDX Upsert handler](https://github.com/MewoLab/AquaDX/blob/v1-dev/src/main/java/icu/samnyan/aqua/sega/ongeki/OngekiUpsertAllApi.kt) preserves omitted lists and uses the existing target user when `userData` is absent; the [controller](https://github.com/MewoLab/AquaDX/blob/v1-dev/src/main/java/icu/samnyan/aqua/sega/ongeki/OngekiController.kt) can return a success-looking response for an unsupported API. Therefore `returnCode=1` alone never establishes success: a fresh complete target read must retain every pre-upload best and contain every expected improvement. Successful synchronization keeps the combined local best view and folds in any higher target scores discovered during the reads; separate direct-read archives retain the actual server rating and resources. Partial writes, rejection, unsupported no-op behavior, cancellation, and failed verification report failure while retaining the local merged archive and target backup. Retrying rereads the target and sends only remaining improvements.

Missing technical ranks are inferred using the local game's score thresholds; missing platinum stars are inferred only when compatible local chart metadata supplies its total platinum maximum. Protocol platinum rank 6 represents the five-star Ex level, which the rating display caps to five. Without a maximum, a missing source star level is not inferred. New chart rows with zero play count are loaded and considered by the game's `UserNewRating.calcBest`, but the game's cumulative music-score totals exclude zero-play rows. Server rating values are not overwritten and may remain unchanged until the game recalculates them.

The upload adapter is tested with temporary archives and local fake ALL.Net HTTP, AimeDB AES packets, and game endpoints, including partial batch failure and success-looking no-op responses. Tests verify no ALL.Net User-Agent, the game identifier on every sync API, API/player separation, keyed BLAKE2b vectors, failure before networking when local metadata is absent, and ordinary standalone read compatibility. Static extraction was checked against installed local game 1.50 without executing the game or revealing the extracted inputs. No real server write has been executed as part of automated validation. The deployed server may impose authentication, update semantics, or restrictions beyond the Aqua-compatible handler. Local game execution is blocked during upload to avoid competing saves; the protocol offers no atomic compare-and-swap against another machine saving the same player concurrently.
